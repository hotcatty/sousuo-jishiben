# Focus Guard · 搜索记事本 产品说明书

> 版本对应 manifest 1.11.0。本文描述的是**代码里已经跑起来的东西**，不是设想。
> 每条规则都能在源码里找到出处，文中标了文件位置，方便你改设计时回查。
> 面向对象：接手做 UI 设计和流程完善的人。

---

## 0. 一句话

用户自己搜、自己决定收什么；插件把收进来的碎片按「板块」组织起来，读出哪些事**已经能定**、哪些**还不能定**，并给出下一步**能直接去搜的词**，最后存成一份可以随时接着补的笔记。

---

## 1. 产品定位与边界

### 1.1 它是什么

一个**搜索过程的容器**。用户在小红书里一次次检索，信息散落在几十条笔记里，这个工具负责把散落的东西收拢成结构，并推动下一次检索。

### 1.2 它明确不是什么

这条边界是产品的立身之本，UI 上任何地方都不该违背：

| 不是 | 原因 |
|---|---|
| 聊天助手 | 没有对话框、没有多轮问答。用户不跟它说话，只往里丢材料 |
| 答案生成器 | 不生成完整行程/方案，不写 Day1/Day2、Plan A/Plan B |
| 内容农场 | 绝不编造材料里没有的事实。宁可说「还不能定」 |
| 进度条工具 | 禁止百分比、完成度、打分。搜索没有「完成」这个客观状态 |

最后两条在给模型的系统提示里是硬性写死的（`src/lib/fg-lib.js` 的 `buildOrganizePrompt`）：

> 不要生成完整行程或方案，不要用 Day1/PlanA 这种模板，不要编材料里没有的事实。
> 禁止百分比和完成度。

### 1.3 适用与不适用

**适用**：目的模糊、需要多轮检索才能收敛的事。旅游攻略、求职调研、装修选购、考研规划。共同特征是**一开始说不清自己要什么，是搜着搜着才清楚的**。

**不适用**：一次检索就能得到答案的事（查天气、查快递）。这类用户不需要容器。

### 1.4 当前平台边界

- 深度适配：**小红书**（`www.xiaohongshu.com`）
- 仅做时间统计：bilibili、抖音
- 记事本本身（侧边栏）与平台无关，任何页面都能打开

## 2. 物理分区：三块画布

产品同时存在于三个地方，设计时要分别对待。

### 2.1 画布 A：小红书页面内（内容脚本注入）

代码：`src/content/xhs-ui.js`（纯 UI 部件）+ `src/content/xiaohongshu.js`（行为逻辑）

两个文件严格分工：`xhs-ui.js` 只负责画和藏，不含判断；`xiaohongshu.js` 负责什么时候画、画完了干嘛。改视觉只动前者。

页面内一共有 9 个浮层部件，全部是临时的、用完就消失：

| 部件 | 函数 | 何时出现 |
|---|---|---|
| 入口闸门 | `showGate` | 首次进入小红书，先问「要搜什么」还是「随便逛」 |
| 首页拦截 | `showHomepageBlock` | 搜索模式下访问推荐首页 |
| 选中气泡 | `showSelChip` | 用户选中一段文字 |
| 板块选择器 | `showBoardPicker` | 收图时选放进哪一块 |
| 图片角标 | `showImgBadge` | 鼠标悬停在图片上 |
| OCR 裁剪层 | `showOcrOverlay` | 点「框选文字」 |
| 跑偏提醒 | `showDrift` | 判定当前笔记跑偏 |
| 久坐询问 | `showCheckin` | 90 秒无操作 |
| 轻提示 | `showToast` | 任何操作反馈 |

**设计要点**：这一层的每个部件都是「打断」，成本很高。除了选中气泡是用户主动触发的，其余都要克制。跑偏提醒和久坐询问都有节流（见 §9）。

### 2.2 画布 B：侧边栏记事本（Chrome Side Panel）

代码：`src/pages/sidepanel.html` + `sidepanel.js`

用的是 Chrome 原生 `sidePanel` API，这一点很关键：**它会挤压网页宽度而不是遮挡**，小红书内容会自适应重排。这是当初专门为了「一直展开着用」而选的方案，不是浮层。

固定 7 个纵向分区，从上到下：

1. **头部**：搜索/闲逛模式切换、本次目的、模型状态
2. **横幅区**（条件显示）：AI 推断出的更清楚的目的 → 可一键采纳；存档成功提示
3. **正在整理**：板块列表 + 新建板块投放区 + 拖放反馈 + 整体还没覆盖的问题 + 本地空间占用
4. **建议接着搜**：关键词 chips，点击直接跳转搜索
5. **你收下的**：原始材料流水
6. **贴一段有用的**：手动输入框 + 「收入」+「收工，存成笔记」
7. **历史笔记**：存档列表，可重开、可删除
8. **DeepSeek**：API key 配置

**设计要点**：分区 3 是绝对主角，其余都是配角。目前的实现里 7 个分区权重太平均，是明显可以优化的地方。

### 2.3 画布 C：Demo 页（自包含演示）

代码：`src/pages/demo.html` + `demo.js`

一个假的小红书 + 真的记事本，用「广州三日游」场景把完整闭环跑通。存在的理由：真实小红书 DOM 会变、网络会抖、AI 会失败，验证产品逻辑需要一个稳定环境。

左边是模拟信息流（含一张真实的广州分区图，位于 `assets/demo/guangzhou-map.jpg`），右边是功能完整的记事本。

**注意**：demo.js 和 sidepanel.js 是**两套独立实现**，共用后台和 `fg-lib.js`，但 UI 代码不共享。改一处要记得改两处。这是技术债。

## 3. 数据模型（设计的骨架）

UI 长什么样可以变，但这四个对象的结构决定了信息能怎么组织。

### 3.1 Session（当前这次搜索）

存储键 `fg_session`，同一时间只有一个。定义见 `src/background/index.js` 的 `emptySession()`。

```
{
  id, noteId,            // noteId 非空 = 这是从历史笔记重开的
  intent,                // 本次目的，用户输入的原始关键词
  platform, startedAt,
  clips: [],             // 材料，最多 200 条；满了明确拒收，绝不静默丢
  boards: [],            // 板块
  summary: {},           // AI 整理结果
  proposals: [],         // AI 想动旧结构的提议，等用户点头，最多 6 条
  lastDiff: null,        // 上一次整理改了什么，UI 拿它做高亮
  organizing,            // true = 正在跑整理，按钮禁用
  driftEvents: [],       // 跑偏记录，最多 20 条
  positiveLabels: [],    // 用户纠正过的「这就是我要的」，最多 20 条
  naggedNoteIds: [],     // 已经唠叨过的笔记，避免重复打断，最多 40 条
  lastDriftPopupAt,      // 打断节流用
  keywords: []           // 推荐搜索词
}
```

### 3.2 Clip（材料）

一条收进来的东西。**这是最小信息单位**。

```
{
  id, title,             // 标题上限 120 字
  text,                  // 正文上限 20000 字，装得下一整篇长笔记
  topics: [], url,
  source,                // 来源，见下表
  boardId,               // 归属板块；空 = 还没归位
  analyzed,              // false = AI 还没读过它，计入「整理这 N 条」
  truncated,             // 0 = 完整；非 0 = 原文字数，界面上明说被截了
  image,                 // 图片，可为 null
  at
}
```

`analyzed` 和 `boardId` 两个布尔组合出三种状态，直接决定它显示在哪：

| analyzed | boardId | 状态 | 显示位置 |
|---|---|---|---|
| false | 空 | 待整理 | 暂存区 |
| false | 有 | 用户拖进某块了，AI 还没读 | 板块里，同时计入整理按钮的数字 |
| true | 有 | 已整理 | 板块里 |

`Lib.pendingClips()` 取第一种，`Lib.unorganizedCount()` 取前两种之和（就是按钮上的数字）。

`source` 的取值决定了它是怎么进来的，UI 上可以据此区分展示：

| source | 含义 |
|---|---|
| `selection` | 在小红书页面选中文字收入 |
| `paste` | 在侧边栏手动粘贴 |
| `drag` | 拖拽文字进板块 |
| `image` | 收图（含 OCR 文字或纯图） |
| `ocr` / `ocr-manual` | 图片文字提取，后者是手打的 |
| `correct` | 用户纠正跑偏判断时顺手收下的 |

### 3.3 Board（板块）

**板块是有身份的持久容器，不是每次重新生成的分组**。这是整个产品最重要的设计决定。

```
{
  id,                    // 稳定 id，AI 更新时靠它认人
  name,                  // 上限 40 字
  clipIds: [],           // 归属的唯一真相，一条材料只能挂在一个板块下
  settled: [],           // 已经能定，最多 10 条，只增不改
  unsettled: [],         // 还不能定，最多 8 条
  keywords: [],          // 继续搜这块的词，最多 4 条
  pinned,                // true = 用户自己建的，一条材料都没有也要留着
  updatedAt
}
```

`pinned` 的意义：允许用户**先搭骨架再往里填**。比如先建「住宿」「交通」两个空板块，再慢慢收集。AI 不许删除它们。

板块上的所有内容都可以由用户直接改：`RENAME_BOARD` 改名、`DELETE_BOARD` 删块（材料退回暂存区，不丢）、`EDIT_FACT` 增删一条结论、`REMOVE_CLIP` 删材料、`ASSIGN_CLIP` 挪材料。改完之后 AI 沿用改后的样子，见 §4.2。

### 3.3.1 Diff（上一次整理改了什么）

`session.lastDiff`，整理时生成，UI 用它做高亮和那句「这次整理：…」。

```
{
  at, source,            // 'llm' 或 'local'
  newBoards: [boardId],
  newClips:   { boardId: [clipId] },
  newSettled: { boardId: [text] },
  resolved:   { boardId: [text] }   // 这次从「还不能定」变成能定的
}
```

设计上需要三种标记：新板块整块高亮 + 「新」角标、新增的 settled 带「新」角标、被解决的 unsettled 划掉并显示「这条现在能定了」。

### 3.4 Note（存档的笔记）

收工产物。每条笔记单独一个存储键 `fg_note_<id>`，另有一个轻量索引 `fg_note_index` 存列表页要用的摘要信息。

**分开存是有原因的**：笔记里含图片 base64，可能上百 KB；索引要频繁读写来渲染历史列表。混在一起会让每次列表刷新都搬运几 MB 数据。索引条目实测 151 字节，测试里锁死了「索引中绝不能出现 base64」这条不变量（`eval/notes.test.js`）。

笔记完整保留板块结构（不是拍平成文本），所以重开后能无损接着补。

## 4. 主流程

```
进入小红书
   │
   ├─ 闸门：搜什么？ ──→ [闲逛] 只统计时间，不干预
   │                    [搜索] ↓
   ▼
搜索模式（侧边栏自动打开）
   │
   ├──→ 浏览笔记 ──→ 跑偏判定 ──→ 跑偏就提醒（可纠正/可改目的）
   │
   ├──→ 收材料：选中文字 / 收图 / 手动粘贴 / 拖拽
   │         ↓
   │    落进「待整理」暂存区（不惊动 AI，不动已有板块）
   │         ↓
   ├──→ 用户点「整理这 N 条」 ──→ AI 只读这 N 条，往现有板块上加
   │         ↓
   │    板块更新：归位 + 新增判断 + 消解「还不能定」+ 该搜什么
   │         ↓
   │    显示 diff：这次新建了几块、新增几条判断、几件事现在能定了
   │         ↓
   ├──→ 点推荐词 ──→ 发起新检索 ──→ 回到收材料（闭环）
   │
   ├──→ 拖拽补全：把材料拖进某块（直接落位）/ 拖出新板块
   │
   ├──→ 不满意：改名 / 删块 / 删材料 / 删结论 / 写自己的判断 / 全部重新生成
   │
   ├──→ AI 想动旧结构 ──→ 写成提议 ──→ 用户点头才执行
   │
   ▼
收工 ──→ 存成笔记 + 清空当前会话（没整理的进「还没整理」，不丢）
   │
   └──→ 历史笔记 ──→ 重开 ──→ 回到搜索模式，接着补
```

### 4.1 闭环的关键

「点推荐词 → 新检索 → 收材料 → 整理 → 新推荐词」是产品的**心跳**。设计上必须让用户随时能看到「下一步搜什么」，这是驱动力来源。

### 4.1.1 为什么整理是手动的

早期版本每收一条就自动跑一次 AI。放弃了，原因不是贵，是**吵**：用户连收 5 条时板块会在眼皮底下重排 5 次，而模型有随机性，板块名和材料位置会来回跳，用户刚记住的布局转眼就变了。顺带的好处是成本——同一个 20 条材料的会话，每条都整理约 8.5 万 token 输入，攒着整理约 2.3 万。

所以规则是：**收材料是用户的事，随时可做且零延迟；整理是一次显式动作，用户决定什么时候交给 AI。** 按钮上必须带数字（「整理这 3 条」），这个数字替代了自动整理提供的「系统在跟进」的安全感。

### 4.2 只增不改（append-only）

一旦某块内容被用户看过并默认接受，它就从「AI 的输出」变成了「用户的东西」，第二轮整理不许推翻。代码层硬约束，不是 prompt 里的软请求：

| 字段 | 增量整理时 |
|---|---|
| 板块名 | 冻结。模型返回新名字也不采纳，只能写成 rename 提议 |
| 已有 settled | 冻结。只能追加，不能修改或删除已有条目 |
| 已有材料归属 | 冻结。模型的 `place` 只对本轮新材料生效 |
| unsettled | 只有模型在 `resolved` 里点名某条 U 编号，那条才移除；漏掉的留着 |
| keywords | 可整体替换（它是建议，不是结论） |

唯一允许的自动变化是 **unsettled → settled**，因为那是用户想看到的进展，不是推翻。

唯一允许推翻的入口是用户主动点「全部重新生成」，它会推平所有板块、清空用户改动，让全部材料重排一次，前面有确认弹窗。

### 4.2 结束语义

明确选择了**归档**而不是「完成」：存成历史笔记并清空当前会话，但随时能重新打开接着补。没有「已完成」状态，因为搜索本来就没有终点。

重开后 `session.noteId` 会指向原笔记，再次收工时**更新原记录而不是新建一条**，`startedAt` 也保留原值（`finishSearch` / `reopenNote`）。

## 5. 交互逻辑清单

### 5.1 入口闸门

**触发**：首次进入 `xiaohongshu.com`，且 sessionStorage 里没有本标签页的决定。
**内容**：输入框（带上今天用过的关键词）+「开始搜」+「随便逛逛」。
**行为**：
- 选「开始搜」→ 打开侧边栏 → 创建会话 → 跳转搜索结果页
- 选「随便逛逛」→ 打开侧边栏 → 切 browse 模式 → 不再干预

**边界**：决定存在 `sessionStorage`（标签页级），关掉标签页重开会再问一次。关键词存在 `chrome.storage.local` 的 `xhs_keyword_<今天日期>`，**按天过期**。

### 5.2 首页拦截

**触发**：搜索模式下访问推荐首页。
**行为**：盖一层，给「回到搜索」和「就想逛逛」两个出口。选后者立即切 browse 并不再拦。

**设计理由**：推荐流是注意力黑洞，进了就出不来。但必须给逃生出口，否则是在跟用户对抗。

### 5.3 收文字

**触发**：在小红书页面选中文字（`mouseup`）。
**呈现**：选区旁弹出卡片，第一个按钮是「收入记事本」（让 AI 归类），后面跟着当前所有板块的按钮（直接指定归属）。
**反馈**：toast「已放进『XX』，正在补这一块」或「已收入，右侧正在整理」。

**边界**：空选区 → 提示「先选中一段文字」。点击卡片内部不关闭卡片（靠 `closest('#fg-selchip')` 判断）。

**整页保存**（`addWholeNote`）取 `extractNoteSignals().body`，即正文容器的完整 `innerText`（在 `.note-content / #detail-desc / .note-text / .desc / article` 里取最长的那个命中）。注意区分两个字段：`snippet` 只截 400 字、只喂跑偏判定；`body` 是收录用的全文，不截。早期版本两者共用 `snippet`，导致整页保存只存下开头 400 字。

### 5.4 收图（四种方式）

| 方式 | 位置 | 说明 |
|---|---|---|
| 悬停收图 | 小红书页 | 鼠标移到图上 → 「收这张图」→ 选板块 |
| 拖图片文件 | 侧边栏 / Demo | 从 Finder 直接拖进板块 |
| 拖页面里的图 | Demo | 拖 `<img>` 或图片链接 |
| 粘贴 | 侧边栏 / Demo | 先点一下板块选中它，再 Cmd+V |

图片规则见 §10。

### 5.5 拖拽

放置区能识别四种数据，按优先级：

1. `application/fg-clip` → 材料在板块间移动
2. `dataTransfer.files` 里的图片 → 收图
3. `text/uri-list` 或 HTML 里的 `<img src>` → 收图
4. `text/plain` → 收成文字材料

认不出来时给明确提示（「这个东西认不出来。可以拖图片、页面里的图，或者选中的文字」），不静默失败。

**新建板块**：拖到「拖到这里 = 新建一个板块」区域，用内容前 12 个字当板块名。也可以点按钮建空板块。

### 5.6 跑偏提醒

**内容**：本次目的 + 当前笔记标题 + 三个出口：
- 「回搜索」→ 记录一次 pulled_back
- 「这就是我要的」→ 存入 positiveLabels（影响后续判断）+ 顺手把这条收成材料
- 「改目的」→ 把本次目的换成这篇笔记的方向，重新整理

**设计要点**：第三个出口很重要。目的本来就是搜着搜着才清楚的，「跑偏」有时候其实是「找到了真正想要的」。

### 5.7 久坐询问

**触发**：搜索模式 + 页面可见 + 90 秒无 click/keydown/wheel + 当前没有其他浮层。检查间隔 15 秒。
**出口**：「还在搜」/「先歇会」/「收工」。

另有一个独立的定时打断（`chrome.alarms`），周期由设置里的 `interruptInterval` 决定，默认 0 即关闭。

### 5.8 收工与重开

**收工**：点「收工，存成笔记」→ 存档 + 清空 + 横幅显示存档结果。
**边界**：一条材料都没有时拒绝，返回 `EMPTY_SESSION`。
**重开**：历史列表里点「接着补」→ 恢复成当前会话。「删掉」直接删。

## 6. AI 怎么运转

### 6.1 两级模型 + 三级降级

代码：`chatJson` / `describeAi`（`src/background/index.js`）

```
配了 DeepSeek key？
  ├─ 是 → 调 DeepSeek，失败就记录错误并显示出来（不悄悄降级到本机模型）
  └─ 否 → Chrome 本机模型（LanguageModel API）可用？
            ├─ 是 → 用它
            └─ 否 → 纯本地规则归类
```

三种状态在侧边栏顶部有明确标识，**失败必须可见**。这是之前踩过的坑：AI 静默失败导致界面看起来「什么都没发生」。

DeepSeek 调用参数：`temperature 0.2`、`response_format: json_object`（服务端 400 时自动去掉重试）、整理用 `max_tokens 2600`、跑偏判定用 `220`。

错误信息全部翻译成人话（`humanizeApiError`）：401 → 「Key 无效或已过期」，402 → 「余额不足」，429 → 「请求太频繁」，输出截断 → 「模型输出被截断（材料太多），已换本地归类」。

### 6.2 触发时机

**只有用户点「整理这 N 条」才会调模型**（`ORGANIZE_NOW` → `organizeNow`）。收材料、拖拽、改名、删条目都不触发。

一次整理只处理 `analyzed === false` 的那批材料。跑完这批全部标记为已整理，暂存区清空。

整理期间 `session.organizing = true`、`summary.thinking = true`，按钮禁用并显示「正在整理…」。

### 6.2.1 增量 prompt：输入量不随会话滚雪球

`buildOrganizePrompt` 给模型的东西分三段：

1. **现有板块**：名字、材料的 `#` 引用、settled、unsettled（带 U1/U2 编号供 `resolved` 点名）。不含任何材料正文。
2. **已有材料**：每条一行，`clipPreview(c, 40)` 再整体截到 64 字符。只为让 proposals 能引用它们。
3. **本轮新材料**：给正文。单条最多 1600 字，整批不超过 20000 字，条数多时按 `20000 / 条数` 分摊（保底每条 400 字）。真被截的会附上「正文还有 N 字没给你，按已给的部分判断，不要猜后面」。已经被用户拖进某块的会标「用户已经放进 B2，不许挪走」。

对比旧的全量重发（每轮重发最近 18 条正文，输入是 O(N)），现在每轮输入接近常数。

模型输出契约（`place` / `new_boards` / `updates` / `proposals`）见 `buildOrganizePrompt`，合并规则见 `mergeOrganizeResult`，硬约束见 §4.2。

### 6.2.2 提议通道

模型想改名、拆分、合并、挪动旧材料，只能写进 `proposals`，不能自己执行。四种可执行类型：

| kind | 字段 | 执行效果 |
|---|---|---|
| `rename` | `board`, `to` | 改板块名 |
| `merge` | `board`, `into` | 把前者的材料和结论并进后者，删掉前者 |
| `split` | `board`, `clips`, `to` | 把指定材料拆成新板块 |
| `move` | `clips`, `into` | 把指定材料挪进某块 |

UI 上是一张卡片：一句人话 + 理由 + 「好，这么改」/「不用」。视觉上复用 `intent-box`（「方向更清楚了 → 就按这个搜」）那套模式。每轮最多 3 条，会话里最多留 6 条。

### 6.3 给模型的契约

板块用 `B1/B2` 引用，材料用 `#1/#2` 引用，每条 unsettled 用 `U1/U2` 引用。模型返回：

```json
{
  "place": [{"clip": "#8", "board": "B1"}],
  "new_boards": [{"name": "", "clips": ["#9"],
                  "settled": [], "unsettled": [], "keywords": []}],
  "updates": [{"board": "B1", "settled_add": [], "resolved": ["U1"],
               "unsettled_add": [], "keywords": []}],
  "proposals": [{"kind": "rename|split|merge|move", "board": "B1",
                 "into": "B2", "to": "", "clips": ["#3"], "why": ""}],
  "emerging_intent": "比原始关键词更清楚的一句话目的",
  "intent_ready": true,
  "next_searches": [{"keyword": "", "why": ""}],
  "still_open": [],
  "quiet_nudge": "一句整理完的旁白"
}
```

注意这里没有「重新输出全部板块」这种字段。模型只能描述**增量**，结构上就不给它推翻的机会。

### 6.4 模型之后的硬约束

**不信任模型输出**，`mergeOrganizeResult` 会逐条纠偏：

1. 板块名、已有 settled、已有材料归属一律以本地为准，模型改了不采纳（§4.2）
2. `place` 只对本轮新材料生效；已经有归属的材料，这一轮谁也挪不动
3. `resolved` 只认真实存在的 U 编号，没点名的 unsettled 留着——模型忘了也不会丢
4. 模型漏掉的新材料，用本地规则兜底重新归位，**不许凭空消失**
5. 用户的空 `pinned` 板块永远保留
6. 数量截断：新板块每轮最多 4 个、提议最多 3 条，settled 最多 10 条、unsettled 8 条，每块 keywords 4 条，next_searches 6 条，still_open 5 条

**这一层是产品可靠性的关键**。模型会漏、会瞎改，但用户认下的东西和手工操作必须永远生效。

## 7. 信息规则

### 7.1 settled / unsettled 的定义

这两个词是产品的核心表达，措辞在代码里是定死的：

- **已经能定**（settled）= 综合该板块材料能下的判断
  例：「这条线以广州塔和夜游为核心，适合傍晚到夜间」
- **还不能定**（unsettled）= 材料还不支持的结论，或缺了它就没法下判断的东西
  例：「没说各点之间耗时，排不了时间表」

**关键机制**：每次整理，AI 要检查上一版的 unsettled 是否已经能定；能定了就在 `resolved` 里点名它，那条才移到 settled。这就是「越补越全」的具体实现，也是唯一允许自动发生的「减法」。

> 历史说明：这两项早期叫「加分项/减分项」，用户反馈看不懂——那是评价语气，而这里表达的是**确定性程度**，不是好坏。改名后语义才对上。设计时请勿退回评价类措辞。

### 7.2 本地归类规则（无模型时）

`localOrganize` 只处理本轮新材料，已有板块的名字、结论、材料一概不碰。新材料的归属优先级从高到低：

1. 用户手动指定的板块（拖进去时就已经落位，整理时跳过）
2. 规则匹配 `THEME_RULES`，命中关键词最多的那条；同名板块已存在就并进去
3. 都不中 → 丢进「还没归类」

内置 7 条规则：岗位要求、招聘信息、经验与观点、片区与路线、推荐名单、背景与故事、票务与避坑。明显偏向求职和旅游两个场景，其他领域会大量落入「还没归类」。**这是当前最明显的覆盖缺口。**

板块保留条件：有材料 **或** 是用户建的（pinned）。

### 7.3 图线索优先

`【图线索】` 开头的材料（来自 OCR 或收图）被当作**结构底图**，优先建成「片区/骨架」类板块，不拆成散点。

这对应用户那个具体场景：一张「广州分三个板块」的图，本身就是攻略的骨架，不该被打散成三条孤立的摘录。

## 8. 推荐搜索关键词规则

这是驱动闭环的发动机，规则最细。

### 8.1 组装优先级

`suggestKeywords` 按顺序取，去重，**最多 8 条**：

1. AI 给的 `next_searches`
2. 各板块的 `keywords`
3. `still_open` + 未覆盖的 checklist 项，各自拼成 `原始目的 + 缺口`（最多取 3 条）
4. 兜底：有材料 → `目的 + 经验分享`
5. 再兜底：只有 `目的` 本身

### 8.2 对 AI 生成词的要求

写在系统提示里：

> keywords 和 next_searches 必须具体到能搜出新笔记（「广州塔的由来」而不是「继续了解」）。每个板块至少 1 个 keyword。

判据是**能不能直接粘进搜索框搜出东西**。「继续了解」「深入研究」这类不合格。

### 8.3 无模型时的本地兜底

`guessNextSearches` 按场景硬编码，最多 6 条：

| 场景（正则匹配目的） | 产出 |
|---|---|
| 设计/产品/岗位/招聘/求职/面试/转行 | `目的+岗位要求`、`目的+真实经历`、`目的+转行` |
| 旅游/三日/攻略/景点/游玩 | `目的+分区 路线`、`目的+历史 故事`、`目的+门票 避坑` |

每条都带一句 `why`（为什么值得搜），UI 上应该展示——这是说服用户点击的理由。例：「先把空间骨架钉住」「问一句为什么值得去」「把可执行细节补上」。

这三条其实隐含了一套**信息收集的递进顺序**：先骨架 → 再理由 → 最后细节。这个顺序值得在 UI 上体现出来。

### 8.4 点击行为

点关键词 chip → `SEARCH_KEYWORD`：如果开着 Demo 页就在 Demo 内部搜，否则把当前标签页导航到小红书搜索结果页。

### 8.5 缺口清单（still_open）

两个来源，二选一：

- 目的能匹配上 `inferChecklist` 的四类场景（家居、减脂、选购、考研）→ 用固定检查清单，逐项判断是否已被材料覆盖
- 匹配不上 → 用 `guessOpenQuestions` 按场景猜（只覆盖求职、旅游）

**注意**：旅游和求职**没有** checklist，只有 guessOpenQuestions；家居等四类**有** checklist。两套机制并存且覆盖面都不全，是需要统一的地方。

## 9. 跑偏判定与打断规则

### 9.1 判定顺序

`classifyHeuristic` 先跑本地规则：

1. 没有本次目的 → `unknown`
2. 标题和正文都空 / 标题是「...」 → `unknown`
3. 匹配目的所属领域（7 个领域词表：家居、学习、饮食、数码、护肤、求职、旅游）
4. 计算三个量：`onHits`（正文命中领域正向词）、`offHits`（命中娱乐词）、`ov`（目的与正文的 token 重合率）

判定树：

| 条件 | 结论 |
|---|---|
| 有领域 且 有娱乐词 且 无正向词 且 ov<0.35 | `drifting` / high |
| 有领域 且 正向词≥1 | `on_goal`（≥2 个或 ov≥0.2 时 high，否则 medium） |
| ov≥0.35 | `on_goal` / medium |
| 无领域 且 有娱乐词 且 ov<0.15 | `drifting` / high |
| 其余 | `unknown`「信息不够，先不打断」 |

**整体倾向保守**：拿不准一律 `unknown`，不打断。误判打断的代价远高于漏判。

### 9.2 模型复核

有模型时再过一遍 LLM，结果覆盖本地判断。但有个硬规则：**LLM 说 confidence 是 low，一律转成 unknown**。

用户纠正过的「这就是我要的」会走 `matchesPositiveLabel` 提前放行（token 命中≥3 个 或 Jaccard≥0.28），不再打扰。

### 9.3 打断节流

弹窗需要同时满足四个条件：

1. 判定为 `drifting`
2. confidence 不是 low
3. 这条笔记没被唠叨过（`naggedNoteIds`，记 40 条）
4. 距上次弹窗 ≥ **12 秒**（`DRIFT_COOLDOWN_MS`）

## 10. 图片规则

### 10.1 存储策略

| 项 | 值 |
|---|---|
| 存档尺寸 | 宽 600px（等比），JPEG 质量 0.6 |
| 实测体积 | 约 56KB / 张（以 766×1024 的分区图实测） |
| 原图 | **不存**，只留 URL，点开回源看大图 |
| 配额上限 | 9MB（`chrome.storage.local` 约 10MB，留 1MB 余量） |
| 容量 | 约 165 张 |

**为什么是 600px**：这类图的价值在小字上（「步行18分钟」「打车10分钟」）。实测 400px 时地名还认得出但分钟数已经糊了，600px 完全清晰。选型依据是可读性，不是体积。

超配额时**拒绝收图并明确报错**（告知已用多少、请删旧笔记），不静默失败。侧边栏底部常驻显示占用量。

### 10.2 AI 与图片的关系（重要）

**AI 读不了图，只能读文字。** DeepSeek 的 `deepseek-chat` 不带视觉；OCR 依赖 Chrome 本机模型（Gemini Nano），大部分浏览器上没开，所以**识别经常失败**。

后果：图收进来了，但板块里的 settled/unsettled 不会因此多出任何一条，图只是配图。

处理方式：
- 识别成功 → 文字存进材料正文，前缀 `【图线索】`，正常参与推理
- 识别失败 → 图照存不误，提示明确告知「AI 只能把它当配图，想让它参与推理，把图里的关键信息打在输入框里收一条」
- 给模型的材料清单里，带图的标 `[带图]`；没识别出文字的附一句**「不要编图里的内容」**，防止它看标题瞎编

最后这条有测试锁定（`eval/notes.test.js`）。

**短期结论：图靠拖，图里的信息靠手打。** 这个落差要在 UI 上诚实表达，不要让用户以为收了图 AI 就看得见。

## 11. 边界条件与失败态

设计时每一条都要有对应的界面表现。

### 11.1 数量上限

| 对象 | 上限 | 超出后 |
|---|---|---|
| 材料 | 200 条 | 拒收并提示「先收工存成笔记，再开一次新的搜索」 |
| 单条正文 | 20000 字 | 截断，并在 `truncated` 里记下原文字数，卡片上明说 |
| 单条标题 | 120 字 | 截断 |
| 板块 | 8 个 | 模型返回超出部分丢弃 |
| 板块名 | 40 字 | 截断 |
| settled / unsettled | 各 6 条 | 截断 |
| 每块 keywords | 4 条 | 截断 |
| 推荐搜索词 | 8 条 | 截断 |
| 喂给模型的材料 | 全部 | 旧材料只给标题占位（每条截 64 字）；新材料给正文，按上面的预算分摊 |
| 图片总量 | 9MB | 拒绝并提示 |

**这些上限不许静默生效**。到顶时要么拒收并说清原因，要么记下 `truncated` 并在卡片上写明，不能让用户以为收全了。

界面上也不做截断：卡片里渲染的是完整正文，用 CSS 夹成 4 行，真被夹住的才长出「展开全文」；超过 200 字的材料在来源行上报字数，方便用户核对有没有收全。

### 11.2 空状态

| 场景 | 表现 |
|---|---|
| 没开始搜索 | 「还没有开始这次搜索」 |
| 0 条材料 | 「选中有用的文字，点『收入记事本』。收进来只是先存着，攒几条再点整理」 |
| 暂存区为空 | 「空的。在左边收东西，会先落到这里，不会立刻打乱右边的板块」 |
| 有待整理但还没点整理 | 「已收 N 条，其中 M 条还没整理。点『整理这 M 条』，已有的板块不会被推翻」 |
| 还没有板块 | 「还没有板块。先收两条，再点上面的『整理』——它不会先给你一份 Day 1/2/3」 |
| 板块为空 | 「这块还是空的，往里拖点东西，或点一下它再粘贴图片」 |
| 无历史笔记 | 空列表 |
| 收工时 0 条材料 | 拒绝，返回 `EMPTY_SESSION` |
| 收工时还有 N 条没整理 | 照存，落进「还没整理」板块，收工提示里说明 |

### 11.3 失败态

| 失败 | 表现 |
|---|---|
| AI 调用失败 | 橙色错误条 + 具体原因 + 「再整理一次」按钮，这一批先用本地关键词归类兜底（材料不会丢） |
| Key 无效 / 余额不足 / 限流 | 顶部状态条给人话原因 |
| 输出被截断 | 「模型输出被截断（材料太多），已换本地归类」 |
| OCR 失败 | 图照存，提示改用手打 |
| 图片下载失败 | 「图片下不下来，把能选中的字收入即可」 |
| 空选区 / 空材料 | 「先选中一段文字」/「这段是空的」 |
| 拖了认不出的东西 | 明确说明能拖什么 |
| 存储满 | 报出已用量，建议删旧笔记 |

**统一原则：任何失败都要可见、可理解、有下一步。** 这是从「按钮点了没反应」那次问题里定下的规矩。

### 11.4 进度阶段

`computeProgress` 按材料条数分三档，只影响提示文案：

- **early**（0–2 条）：「已收 N 条，正在按板块整理，并给出下一步该搜什么」
- **mid**（3–7 条）：「已收 N 条，正在按主题整理，不打断你」
- **late**（≥8 条）：「已收 N 条，主题已经能看了。继续搜，或停下来看整理」

`coveragePct` 字段存在但**永远返回 null**——刻意的，对应 §1.2 的「不做进度条」。

## 13. 已知缺口

做设计时会撞上的，先列清楚。

### 13.1 覆盖面不全

- `THEME_RULES` 只有 7 条，偏向求职和旅游。其他领域大量落入「还没归类」
- `inferChecklist` 只覆盖家居、减脂、选购、考研；`guessOpenQuestions` 只覆盖求职、旅游。两套机制并存且都不全
- 本地兜底的推荐词只有求职和旅游两类

### 13.2 能力落差

- AI 看不见图（§10.2）
- OCR 在多数浏览器上不可用
- 没有导出功能（已明确本期不做，但笔记里已经有图，导出 Markdown / 单文件 HTML 是顺手的）

### 13.3 技术债

- `demo.js` 和 `sidepanel.js` 是两套独立 UI 实现，改一处要改两处
- `clusterThemes`、`buildWrapup`、`roundCoveragePct` 是早期遗留，仍在导出但主流程已不用

### 13.4 留给设计决策的

- 侧边栏 7 个分区权重太平均，主次不分
- 板块内部：材料、settled、unsettled、keywords 四类信息目前平铺，缺少视觉层次
- 「还不能定」→「已经能定」的迁移是核心价值，但现在只是静态列表，用户感知不到变化发生
- 推荐词的 `why` 有数据但展示很弱
- 历史笔记列表信息（几个板块、几条材料、几张图、几件还不能定）已经算好了，但呈现简陋
